# MVP 路线图

## 1. 目标

本路线图描述从当前仓库骨架到“支持好友开房对战的网页版南京麻将敞开头游戏 MVP”的阶段路径。

MVP 的最终完成标准见 `docs/product-requirements.md`。南京麻将敞开头规则以 `docs/nanjing-mahjong-rules.md` 为唯一权威来源。

## 2. 阶段路线

### a. MVP 文档归位

- 明确 MVP 不是单机 demo，而是四人好友开房联机游戏。
- 明确完整一将必须自动推进和结束。
- 明确文档、架构、规则来源和暂不实现范围。
- 输出 `docs/product-requirements.md`、`docs/mvp-roadmap.md`、`docs/architecture.md`，并修正规则文档中的旧目标冲突。

### b. RuleSet 架构

- 在 `packages/game-core` 中引入可扩展 RuleSet / variant 概念。
- 当前只注册并实现 `nanjing-open`。
- 保持接口足够支持未来 `nanjing-jinyuanzi` 和其他麻将玩法。
- 不提前实现未来玩法的复杂功能。

### c. 完整发牌与初始补花

- 实现四人完整发牌。
- 实现庄家14张、闲家13张。
- 按规则执行初始补花顺序。
- 处理初始补花中的连续补花、花杠结算和无牌可补。

### d. Match / Hand 一将系统

- 建立 `MatchState` 和 `HandState` 边界。
- `Match = 一将牌`，`Hand = 一局`。
- 记录 `matchStatus`、`handStatus`、`currentHandIndex`、`effectiveDealerTurns`、`dealerSeat`、`currentSeat` 和 `cumulativeScores`。
- 支持16个有效庄次和第16局特殊续庄。
- 自动判断一将结束。

### e. Reaction system

- 建立弃牌、补杠等动作后的响应窗口。
- 支持胡、碰、明杠、抢补杠、过。
- 按规则实现 `胡 > 碰 / 明杠`。
- 支持一炮多响。
- 对未确认的响应超时、倒计时或 UI 表达记录 open questions，不自行猜测。

### f. 胡牌型识别

- 实现普通结构、七对、龙七对等基础结构判断。
- 实现门清、对对胡、全球独钓、混一色、清一色、无花果、压绝、天胡、地胡、花开、杠开等规则文档已确认牌型。
- 所有牌型判定必须有测试覆盖。

### g. 计分与实时结算

- 实现456、花二计分。
- 实现点炮、自摸、一炮多响和抢杠胡计分。
- 实现实时结算：花杠、明杠、补杠、暗杠、跟打一圈、同牌打四张、四风归齐。
- 实现比下胡翻倍。
- 保留完整得分记录，便于前端展示结算明细。

### h. 承包 / 包子系统

- 实现杠后承包。
- 实现三嘴包子、三清包子、全球包子和杠开包子。
- 实现承包优先级。
- 确保承包只改变付款人，不改变牌型基础判定。

### i. Room server

- 在 `apps/server` 中实现房间生命周期。
- Room 包含唯一 `roomId`、4 个 player slots、房主、连接状态、准备状态和当前 match。
- 服务端持有权威 Room / Match / GameState。
- 所有客户端动作都必须绑定玩家、座位和房间校验。

### j. 分享链接加入房间

- 创建房间后生成可分享链接。
- 链接携带 `roomId` 或等价房间定位信息。
- 访问链接后加入对应房间。
- 满 4 人后允许准备和开始。

### k. 服务端权威状态同步

- 定义 Socket.IO 事件和共享 payload 类型。
- 客户端提交 `GameAction` 意图。
- 服务端验证动作合法性，调用 `game-core` 推进状态。
- 服务端广播更新后的公共状态和玩家私有视图。
- 客户端不得自行推进权威状态。

### l. 玩家私有视图隔离

- 为每名玩家生成独立安全视图。
- 只向玩家下发自己的手牌。
- 公共区只包含公开花牌、副露、弃牌、分数、当前行动位、庄家和结算信息。
- 增加测试，防止其他玩家手牌泄漏。

### m. Web 麻将桌 UI

- 实现浏览器端麻将桌。
- 展示自己的手牌、花牌、副露、弃牌、分数、当前行动位、庄家、一将进度和响应按钮。
- 所有操作按钮只提交意图，不在客户端裁判规则。
- UI 文案与规则相关时必须可追溯到 `docs/nanjing-mahjong-rules.md`。

### n. 四人联机完整测试

- 覆盖四个玩家通过分享链接加入同一房间。
- 覆盖四人准备、开始一将、完整发牌、初始补花、出牌、响应、结算和下一局。
- 覆盖第16局特殊续庄和自动结束一将。
- 覆盖玩家私有视图隔离。
- 覆盖服务端拒绝非法动作。

### o. MVP 收尾

- 补齐用户可见错误状态和基础空状态。
- 清理与 MVP 目标冲突的旧文档。
- 确认非 MVP 功能没有混入完成标准。
- 运行格式、lint、typecheck、test、build。
- 形成可供后续迭代继续开发的稳定基线。

## 3. 阶段顺序约束

- 任何规则变更必须按“规则文档 → 测试 → 代码”的顺序推进。
- 发现规则未覆盖的问题时，先记录到 `docs/open-questions.md`。
- 不允许为赶进度在 UI、server 或网络层写死南京敞开头规则。
- 不允许用房主手动结束整场替代自动完成一将。
