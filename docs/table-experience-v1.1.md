# V1.1：牌桌体验完善（Table Experience Improvement）

更新日期：2026-10-19。

本文档是 V1.1 牌桌体验改造的主要需求与验收依据。南京麻将玩法、胡牌资格和计分规则仍以
[`nanjing-mahjong-rules.md`](nanjing-mahjong-rules.md) 为唯一权威来源；本文档只约束牌桌状态、
操作反馈、最近记录、结算信息层级、基础音效与简单动画，不修改玩法规则。

## 1. 改造背景与目标

本项目定位是南京麻将专属的好友游戏平台，目标是让四位熟人方便地打完一将南京麻将；它不以
雀魂等综合麻将运营平台为对标对象，也不扩展账号、匹配、养成或商业化能力。

当前版本已经支持四人联机完成一将牌，具有服务端权威裁判、安全玩家视图、掉线暂停、房间恢复、
逐项计分说明和付款明细。V1.1 的重点不是增加平台功能，而是改善一将牌内部的操作反馈和信息呈现：

- 玩家看得懂当前轮到谁、牌桌正在等待什么、牌局为何暂停；
- 玩家提交操作后立即知道正在确认，并在服务端确认后看到明确结果；
- 碰、杠、胡、流局和结算等关键变化有可理解的文字说明；
- 刚才发生的公开事件能够回看，刷新或重连后不会丢失；
- 结算先给出易读摘要，同时保留完整的计分和付款依据。

第一阶段只实现 Demo 级体验。优先保证信息清楚、反馈可靠、等待不迷茫、结算有解释、历史可查询；
不追求精美特效、复杂动画、专业音效或商业化系统。

## 2. 功能范围

### A. 统一的牌桌事件

建立由服务端权威状态推进产生、服务端确认、按确定顺序排列的公开牌桌事件。事件是状态变化的
事实记录，不是客户端根据两个 `RoomView` 快照差异推测出的结果。

事件系统必须满足以下约束：

- 事件 ID 在同一房间生命周期内唯一且持续递增；事件的先后顺序由独立、确定的顺序字段表达，
  不能依赖时间戳。时间戳只能用于展示。
- 同一个命令造成多个连续变化时，服务端按真实推进顺序生成多个事件；重试同一 `commandId` 不得
  重复追加事件。
- 事件只在对应动作已经被服务端接受并推进权威状态后产生。客户端点击、乐观状态或单纯的
  `RoomView` 变化不得生成成功事件。
- 事件保存于现有房间状态中，并随现有 `SavedRoom`/`CloudRoom` 持久化；刷新、短暂断线和同身份
  重连后，从服务端恢复同一批记录。
- `RoomView` 仍按玩家分别生成。公开事件可以进入每位玩家的安全视图，但其公开字段必须一致，且
  不得携带隐藏手牌、牌墙顺序、私有响应、未公开操作资格、会话标识、内部裁判状态或 action token。
- 摸牌事件对其他玩家只表达“某玩家摸牌”等公开事实，不公开所摸牌面；只有原有私有手牌视图可以
  向牌的所有者显示牌面。事件 ID 不得复用命令 ID、会话 ID 或 action token。
- 事件首先服务于最近记录和文字通知；后续音效与动画也必须消费同一已确认事件流，并以事件 ID
  去重，不建立第二套变化推测机制。

V1.1 事件至少覆盖：开手、摸牌、出牌、补花、碰牌、明杠、暗杠、补杠、胡牌、流局、实时计分和
单局结算。事件类型和最小字段在第 01 步定稿，本文档不提前把实现类型固定为某一种 TypeScript
结构。

第 4.8 节已回补特殊规则成立与嘴数锁定关系事件；第 06 步后续通知消费遵循第 4.7 节。

### B. 牌局状态与操作反馈

牌桌持续明确显示以下互斥或可组合状态：

- 轮到哪位玩家出牌；
- 正在等待地胡决定或碰、杠、胡、过等响应；
- 正在等待其他玩家完成私有响应，但不暴露其具体选择或可选资格；
- 有玩家离线时牌局已暂停，以及正在等待哪些玩家重连；
- 本手已结束，正在查看结算或等待下一手。

出牌、碰牌、明杠、暗杠、补杠、补花、胡牌和结算等关键操作必须提供明确的文字反馈，并区分：

1. **操作提交中**：客户端已发出请求，尚未收到权威确认；按钮应防止重复提交。
2. **操作成功**：服务端确认命令并返回相符的权威状态或事件后显示。
3. **操作失败**：服务端明确拒绝时显示可理解的原因，并保持服务端状态。
4. **确认未知**：超时或断线时只能提示“尚未收到确认”并允许使用同一 `commandId` 重试，不能误报
   失败或成功。
5. **等待他人响应**：本人操作已经提交，但响应窗口尚未裁决；最终通知必须服从服务端的优先级、
   抢补杠胡及多家胡牌结果。

界面可以立即显示“正在确认”，但只有服务端确认的操作才能触发成功通知、历史记录、音效或动画。

### C. 最近牌桌记录

牌桌提供可展开、收起的最近记录入口，展示开手、出牌、碰杠、胡牌、流局、特殊规则成立、嘴数锁定
和单手结算等已确认的公开事件。普通摸牌、普通补花及纯计分事件默认不单独展示。

记录生命周期统一规定如下：

- 服务端按从旧到新的顺序保存当前一将最近 100 条公开事件；追加第 101 条时先移除最旧事件。
- 按第 07 步本次要求，入口默认收起，打开后显示当前可用、可展示事件中的最近 20 条，不足则全显；
  按 sequence 从小到大阅读。不增加完整历史或更多详情入口；服务端窗口仍最多 100 条。
- 刷新、断线和重连后以服务端房间存档为准恢复；本地缓存不得覆盖或补造服务端记录。
- 开始“再来一将”时清空上一将的事件列表，与现有分数和 match 重置边界一致，但不得重置房间级
  事件 ID 计数器。提前结束仍保留当将已发生的记录，直至再来一将、离开并切换房间，或房间
  解散/过期。
- 切换房间时客户端立即清除上一房间的展示，只显示新房间下发的记录；不同房间的事件不得合并。
- 真正的旧存档（事件字段和版本标记全部缺失）按空记录兼容加载，不回放或猜测历史；有效的超限
  事件列表在规范化时仅保留最新 100 条，不新增数据库迁移。部分字段缺失或损坏时遵循第 4.4.5 节。
- 清空事件列表、恢复旧存档、裁剪最旧事件或切换手数均不得导致已分配的事件 ID 被重新使用；兼容
  恢复后，房间级计数器必须继续高于该房间已经分配的全部事件 ID。

完整牌谱、任意时间点复盘和跨房间长期战绩不属于最近牌桌记录。

### D. 分层结算界面

单局结算默认突出显示：

- 本手结果（胡牌、流局或其他已确认结果）；
- 胡牌玩家、胡牌方式/主要牌型与关键责任关系；
- 四位玩家本手分数变化及结算后累计分；
- 一至数条主要结算原因。

详细计分项、倍率、公式、承包关系和逐笔付款默认折叠，玩家可以主动展开和收起。已有 `ScoreLine`
中的 `reason`、`winningHand`、`calculation`、`responsibility` 和 `transfers` 应继续复用；旧记录缺少
计算快照时继续只展示已经保存的付款金额，不反推原因。

第 08 步摘要优先直接显示当前手 `hand-settled.changes` 的权威净变化，累计分直接取玩家 `score`。
缺少本手权威汇总时明确标为“未提供”，不将最近 100 项付款窗口误当完整本手账目，不默认零分；
既有付款、公式与计算快照仍可展开。前端不重判牌型、重算金额、倍率、责任关系或累计分。

### E. 基础音效与简单动画

音效和动画必须在统一事件系统、状态提示及最近记录稳定后再加入：

- 只为碰杠、胡牌、流局、结算及特殊成立事件加入基础音效；出牌不播放音效，提供清晰可用的静音设置。
- 音效只响应当前会话中首次看到的已确认事件 ID。初次加载、刷新、重连、流式重复状态和轮询回退
  不得播放已存在的历史事件。
- 静音偏好属于本地展示设置，不改变房间权威状态，也不要求账号或跨设备同步。
- 简单动画限于短促的牌面变化、碰杠高亮和提示淡入淡出，不阻塞点击、响应窗口或下一步操作。
- 尊重系统的 `prefers-reduced-motion` 偏好；减少动态效果时禁用非必要位移和闪烁，仍保留文字反馈。
- 暂不制作复杂特效、角色语音、背景音乐或大型动画编排系统。

## 3. 本次明确不做

以下内容不属于 V1.1 开发目标：

- 账号体系或跨设备身份恢复；
- 人机对战或 AI 教练；
- 随机匹配、段位、排行榜或赛事；
- 角色、商城、付费或养成；
- 完整录像系统或复杂牌谱回放；
- 南京麻将规则重写或计分算法重构；
- 为实现简单提示而重构整个前后端通信架构。

如果后续确需扩展，必须先提出独立需求和方案并完成评审，不能直接混入 V1.1。

## 4. 现有架构与技术约束

### 4.1 当前源码基线

- 浏览器使用 `apps/web/src/cloud-socket.ts` 封装的现有通信层：命令经 HTTP
  `POST /api/command` 提交；房间状态优先通过 `POST /api/stream` 的 NDJSON 流接收，流不可用时回退
  到短轮询。`App.tsx` 仍以类似 Socket 事件的接口消费该封装。
- `cloud/commands.ts` 与复用的 `apps/server/src/table.ts` 负责权威房间状态、合法动作校验、规则引擎
  调用和牌局自动推进。客户端只提交房间命令或服务端签发的 action token。
- `RoomView` 是针对单个玩家生成的完整安全视图，不是可以无差别广播给所有人的统一对象。自己的手牌、
  摸牌标记和操作选项属于私有字段；其他玩家只能看到公开数据。
- `SavedRoom` 保存成员、状态、revision、epoch、match、响应收集、`ScoreLine`、结算倒计时等房间状态；
  云端 `CloudRoom` 在此基础上增加存储格式、房间密钥和时钟字段，并将整体 JSON 保存到现有 D1
  `cloud_rooms.body`。V1.1 最近事件应沿用这个持久化边界。
- 当前 `RoomView` 具有 `paused`、`current`、`phase`、`actions`、`result`、`scores` 和 `tableEvents`。
  第 01B 建立事件数据边界，第 02～04 步接入真实服务端事件。前端已有“正在确认”、等待响应、
  等待重连及结算展示；第 06 步已接入由公开事件驱动的统一即时文字通知，详见第 4.9 节。
- 当前 `room.scores` 保存服务端形成的 `ScoreLine` 快照，安全视图只发送最近 100 项；它是计分账目，
  不能替代包含出牌、碰杠等行为的牌桌事件。

### 4.2 必须保持的机制

- 命令幂等继续使用 `commandId` 和持久化回执；同一命令重试不得再次改变状态、计分或追加事件。
- D1 乐观版本校验、房间 `revision`、规则推进用 `epoch`、响应窗口和按房间/epoch/座位/动作签名的
  action token 必须继续有效。事件顺序字段不能取代这些机制。
- 私有响应收集期间，其他玩家不得得知某人是否能胡、选择了什么或尚有哪些操作。公开事件只能在
  服务端裁决到可公开节点后产生。
- `ScoreLine`、服务端计分说明与付款关系继续复用；前端不重新计算权威牌型、分数或承包。
- 公开事件不得泄露隐藏手牌、牌墙、私有响应、未公开操作资格、内部推导、session、密钥或 action
  token。新增字段必须通过逐玩家安全视图测试。
- 默认不为简单牌桌历史新增数据库表或迁移。只有后续方案经过明确评审，并证明现有房间 JSON
  持久化无法满足容量、并发或查询需求后，才能改变该约束。
- V1.1 不改变 `game-core` 规则结果。事件应记录已经发生的权威变化，不能成为第二套裁判或计分来源。

### 4.3 与历史文档的差异

`architecture.md`、`socket-protocol.md`、`state-machine.md` 和部分实施记录仍描述早期
Socket.IO + SQLite 方案；`table-design.md` 也使用“Socket.IO 回归”措辞。当前 Sites 版本实际采用
HTTP/NDJSON + D1，同时保留原 Node 服务端作为可复用权威牌桌逻辑和历史运行路径。V1.1 实现与验收
以当前 `cloud/`、`cloud-socket.ts`、`table.ts` 和共享类型源码为准，不因旧文档措辞重新引入或重构
Socket.IO，也不在本次文档任务中顺手改写全部历史文档。

### 4.4 第 01A 步：牌桌事件数据契约

2026-10-18 特殊通知补充：第 4.7 节补充本契约的使用范围及待实现的锁定关系事件。
现有版本 1 契约与第 01B 已完成状态保留；补充设计不代表类型、投影或事件生成已经实现。

本节是第 01 步实现前的数据设计依据。它确定公开展示事件的稳定边界，但不声明共享类型、存档字段、
事件生成或测试代码已经实现。

#### 4.4.1 概念与职责

牌桌展示事件是由权威服务端在状态推进完成后形成的、只包含公开事实的不可变记录。它服务于牌桌
文字反馈、最近记录及后续音效和动画，不参与动作合法性、胡牌判定、分数计算或权威状态重建。

牌桌展示事件与 `game-core` 内部规则事件必须分开：

- `game-core` 的 action、`pendingScoringEvents`、`HandResult` 和其他内部状态继续服务于规则推进和
  结算，是权威规则数据；
- 牌桌展示事件属于 `apps/server` 的房间/安全视图边界，是权威状态变化经过公开化处理后的展示
  快照，不得把内部对象原样序列化给客户端；
- 两者不要求一一对应。同一个命令可以按实际推进顺序产生多个展示事件；内部细节可以不展示，多个
  内部结果也可以在最终裁决后形成一个公开摘要；
- 客户端不得使用展示事件反向推进游戏、补算分数或推断未公开状态。

#### 4.4.2 最小公共字段

后续共享类型至少表达下列公共字段。字段名称可在第 01 步实现评审中按现有命名习惯微调，但语义和
约束不得改变。

| 字段       | 语义与约束                                                                                    |
| ---------- | --------------------------------------------------------------------------------------------- |
| `id`       | 房间级正整数事件 ID，用于稳定标识和客户端去重；不得承载命令、会话、版本或 action token 信息。 |
| `sequence` | 房间级正整数确定性顺序，用于排序；不能由时间戳、数组下标或客户端接收顺序代替。                |
| `type`     | 稳定的公开事件种类；只表达展示事实，不直接复用内部 reducer action 或计分事件名称。            |
| `hand`     | 事件所属手数，使用现有对玩家展示的手数语义，便于最近记录分组。                                |

V1.1 不要求公共事件具有时间戳。后续若为展示增加时间戳，它只能是非权威的辅助字段，排序和去重仍分别
使用 `sequence` 和 `id`。不把玩家座位、牌面或结果字段放进所有事件的公共基类；它们只出现在确实需要
这些信息的事件中。

#### 4.4.3 ID、顺序与分配规则

房间状态持久化“下一个事件 ID”和“下一个事件顺序”两个正整数计数器。V1.1 初始实现可以让两者同步
分配相同数值，但它们是语义独立的字段：客户端只能按 `id` 去重、按 `sequence` 排序，不得依赖二者
永远相等。

分配规则如下：

1. 新房间的事件列表为空，两个“下一个”计数器均初始化为 `1`。
2. 每生成一个已确认事件，先读取并分配当前 ID 与顺序，再分别加 `1`；一个命令产生多个事件时，
   必须按权威牌局的实际推进顺序逐个分配。
3. 只有事件与其递增后的计数器一起成功保存，分配才算提交。D1 乐观版本冲突导致整次提交重试时，
   不得把失败尝试中的编号当成已分配编号，也不得产生重复事件。
4. `id`、`sequence` 与 `commandId`、room `revision`、规则推进 `epoch`、action token 完全独立；这些
   现有机制都不能充当事件 ID 或顺序。
5. 切换手数不清空列表也不重置计数器。开始新的一将时清空上一将列表，但保留两个计数器的当前
   值。容量裁剪、刷新、重连和恢复房间同样不得回退计数器或复用编号。
6. “同一房间生命周期”指同一个连续保存的 `SavedRoom` 实体。房间解散或过期、存档删除后，即使
   将来重新创建相同房间号，也属于新的房间生命周期，可以重新从 `1` 开始。

#### 4.4.4 各类事件所需的公开数据

事件联合类型应按事件事实只携带最少数据，不建立一个包含大量可选字段的通用对象。第 01 步只需
为下表预留可辨识的类型边界；具体事件名称和结果摘要的嵌套结构可在对应生成步骤中收窄。

| 事件类别           | 必需的事件专属公开数据                                  | 明确不包含的内容                              |
| ------------------ | ------------------------------------------------------- | --------------------------------------------- |
| 开手               | 庄家座位；必要时包含公开的一将/庄次摘要                 | 发出的具体暗牌、牌墙顺序                      |
| 摸牌               | 摸牌玩家座位                                            | 所摸牌面、实体牌 ID、可用动作                 |
| 出牌               | 出牌玩家座位、已经公开的牌面                            | 该玩家剩余手牌、出牌后的私有资格              |
| 补花               | 补花玩家座位、已经公开的花牌牌面                        | 尾部补入的暗牌、后续私有资格                  |

| 暗杠               | 操作玩家座位、按现有安全视图已经公开的杠牌牌面          | 杠前暗手构成、尾补牌面                        |

| 流局               | 服务端确认的公开流局摘要                                | 牌墙剩余顺序、各家暗手                        |
| 实时计分、单局结算 | 受影响玩家和基于既有 `ScoreLine`/结果形成的最小公开摘要 | 新的前端计分结果、内部 scoring event 原始对象 |

“公开牌面”只表示当前安全视图本来就允许所有玩家看到的牌面。实现时应选择共享的安全牌面表示，不得为了
事件展示直接传输完整的 `game-core Tile`；如果界面不需要实体牌 ID，就不应把实体牌 ID 固定为事件契约。

胡牌、流局和结算的“最小结果摘要”必须来自最终 `HandResult` 和已有 `ScoreLine` 快照，只包含展示最终
结果所需的公开赢家、来源、原因和分数变化。第 01A 步不提前复制 `ScoreLine` 的全部字段，也不确定
第 04 步才能验证的牌型专属结构。

#### 4.4.5 持久化与旧存档兼容

`SavedRoom` 顶层包含 `tableEventSchemaVersion: 1 | 2`、`tableEvents`、`nextTableEventId` 和
`nextTableEventSequence`。版本标记专管牌桌展示事件的存档格式；现有 `SavedRoom.format: 1`、
`CloudRoom.cloudFormat: 1` 和 `rules` 各有原来的职责，不为本次字段扩展改写它们。`CloudRoom`
继承这些字段，并继续把整个房间 JSON 保存在现有 `cloud_rooms.body`；Node 存档也通过同一个
`SavedRoom` 恢复边界。事件、递增后的计数器和命令回执沿用现有 D1 version 校验与原子提交；不新增
数据库表或迁移，不改变 `match`、分数或南京麻将规则。

第 4.8 节回补后新房间使用版本 2，版本 1 继续读取原事件；首次成功追加升级为 2，不补造历史。
版本 2 增加 special-rule-confirmed 与 mouth-locked，版本 1 中出现这两种分支视为损坏。

新建房间和规范化后的内存房间必须同时具有这四个字段。两个计数器都是“下一个可分配值”，必须是
`1` 到 `Number.MAX_SAFE_INTEGER` 范围内的安全正整数；现存事件的 `id`、`sequence` 也必须是该
范围内的安全正整数。分配后若任一计数器无法保持安全整数，则拒绝追加并明确报错，不回绕或复用。
只有从存档读取时允许字段缺失，恢复入口必须统一进行版本判定和运行时校验，不得把 JSON 类型断言
当成校验。

恢复规则按以下顺序执行；“缺失”仅指属性不存在，`null`、错误类型或非法数值都属于损坏：

| 存档情况                                                    | 处理方式                                                                                                          |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 版本标记及其他三个事件字段全部缺失                          | 真正的旧存档：置 `tableEventSchemaVersion: 1`、空列表、两个计数器均为 `1`；不从 `match` 或 `ScoreLine` 补造事件。 |
| 版本标记缺失，但至少一个事件字段存在                        | 版本归属不明：拒绝加载并报事件存档兼容性错误；不得按旧存档初始化。                                                |
| 版本标记存在，但不是整数 `1` 或 `2`（含未来版本）           | 拒绝加载并报不支持的事件存档版本；不得降级。                                                                      |
| 版本为 `1` 或 `2`，列表与两个计数器均有效                   | 原样保留计数器；有效列表超过 100 条时仅裁剪最旧事件，并记录诊断。                                                 |
| 版本为 `1` 或 `2`，列表为空数组且两个计数器均有效           | 原样加载；计数器即使大于 `1` 也不得回退。                                                                         |
| 版本为 `1` 或 `2`，有效列表缺少任一计数器                   | 有效但不完整：拒绝加载；不得由最大 `id` 或 `sequence` 推断编号。                                                  |
| 版本为 `1` 或 `2`，两个计数器有效但列表字段缺失             | 拒绝加载并报告历史缺失；不得以空列表覆盖或继续处理房间操作。                                                      |
| 版本为 `1` 或 `2`，列表为空且任一计数器缺失，或现存字段损坏 | 拒绝加载；不得从历史、列表长度、revision、epoch 或另一计数器猜测编号。                                            |

有效列表要求每条事件满足第 4.4.2 节的公开字段与对应类型的运行时校验，`id` 和 `sequence` 各自
唯一，并按 `sequence` 从小到大排列；`id` 也随列表顺序严格递增。任一已存在的计数器必须严格
大于列表中对应字段的最大值，否则即使可以从列表算出新值，也视为冲突并拒绝恢复，不能覆盖原值。
重复编号、逆序、错误类型、超出安全整数范围或计数器与事件冲突均视为损坏。已经裁剪的历史若
保存了更大的计数器，必须保留更大值，绝不按保留条数或最大值重置。

只有能够独立证明列表完整包含该房间生命周期内此前全部已分配事件时，才可能依据列表最大编号
恢复缺失计数器。当前版本只保存最近 100 条，且再来一将会清空历史；事件存档版本 1 和 2 均
没有记录历史完整性的独立证明。因此本版本遇到任何缺失计数器的新存档都必须拒绝加载，即使列表
非空、少于 100 条、编号连续或从 `1` 开始，也不得假设历史完整。今后若要支持这种恢复，须先设计
可验证的完整性证据并更新存档格式版本与本文档，不能在第 01B 步临时加入推断。

每次成功追加后按 `sequence` 只保留最近 100 条，裁剪发生在编号分配之后，不改变计数器。
开始新的一将时清空列表但保留版本标记和两个计数器。读取时的安全规范化只修改工作副本，后续
经现有成功保存路径写回；不得为修复展示历史单独重置 `match`、分数或整个房间。只有真正的旧存档
和字段完整且有效的版本 `1` 或 `2` 存档可进入此安全规范化路径；有效但不完整的新存档也不能自动补写。

新版本存档不完整或运行时校验失败时，读取路径必须返回明确的事件存档兼容性错误，不生成
`RoomView`、不执行该房间的玩家命令，也不写回原房间；房间相关操作须待存档被人工核查并安全修复
后恢复。即使两个计数器有效但列表字段缺失，也采用这一策略：编号虽可保留，丢失的事件无法恢复，
继续保存空历史会掩盖异常。原始存档留存以便排查；不得重置或覆盖已有牌局状态、已结算分数、
`match`、命令回执或房间版本信息。错误信息应说明是事件历史存档问题，并在诊断中区分“字段缺失”
和“字段损坏”，但不向客户端回显存档 JSON、隐藏牌或会话信息。

#### 4.4.6 安全视图与客户端边界

- `RoomView` 继续逐玩家生成。V1.1 的牌桌事件只有公开版本；同一房间 revision 下，四位玩家收到的
  事件字段必须相同，不为某一玩家在公共事件中夹带私有牌面或操作资格。
- 事件不得包含隐藏手牌、摸牌的具体牌面、牌墙及其顺序、私有响应、未公开操作资格、action token、
  session、房间 secret、内部裁判上下文或未公开的 `game-core` 对象。
- 私人的“命令提交中/失败/确认未知”继续属于发起客户端的命令反馈，不写入公共事件历史。响应窗口
  只有在服务端完成优先级裁决并形成公开事实后才能追加展示事件。
- 刷新和同身份重连后，客户端以新收到的完整 `RoomView` 为准恢复同一事件列表；本地状态不得补造、
  改写或合并事件。初次载入的历史用于展示，不应被当成刚发生的事件重复触发通知、音效或动画。
- 切换房间时立即丢弃上一房间的客户端事件状态。房间暂停、短轮询与 NDJSON 流重复下发不会改变
  事件身份，客户端通过 `id` 去重并通过 `sequence` 排序。

事件生成规则：

- A：成功 START_GAME 产生一次 `hand-started`；初始发牌视为开手的原子组成，不逐张生成摸牌事件。
  初始花牌按引擎庄家起的玩家顺序与各玩家实际花牌顺序公开；然后按引擎补花顺序记录尾部摸牌及新花。
  普通 DRAW_TILE 先记录实际头摸，再按实际尾补次序记录；每张实际取得的牌产生无牌面的 `tile-drawn`，
  花牌随后产生仅含公开牌面的 `flower-replaced`。空墙未取得牌不产生摸牌。成功弃牌产生
  `tile-discarded`，之后由 advance 执行响应或下一次摸牌，保持顺序。
- B：只有新副露实际创建或原碰实际升级时生成 `peng`、`ming-gang`、`an-gang`、`bu-gang`。
  杠成立事件先于其实际尾补和补花。补杠声明打开抢杠窗口不产生成功事件；被抢时原碰未升级，
  因而没有补杠事件。碰/杠来源来自已成立副露；暗杠仅公开原 RoomView 已公开的杠面，不带实体 ID。
  特殊胡替代碰杠时依最终结果记录，不能伪造副露；三清第四杠若引擎未消耗尾牌，不生成尾摸。
- C：动作首次产生最终 HandResult 时记录 `hu` 或 `draw`，自摸、点炮、抢补杠分别用明确摘要区分；
  普通多赢家按结果原有顺序逐人生成 hu，使每名赢家各自的公开付款责任可被准确表达，结算摘要汇总
  全部赢家且不重复。特殊三嘴/三清结果也取最终结果与已有 ScoreLine，不增加规则判定。
  settle 成功消费 pendingScoringEvents 后，逐条从本次已有 ScoreLine 的 transfers 汇总
  `score-changed`；这里只汇总既有付款，不重算金额。动作事实先于该动作的实际分数入账。
  advance 首次成功 completeCurrentHand 后产生一次 `hand-settled`，分差汇总该手已有 ScoreLine；
  completed 状态是幂等边界，不通过可裁剪的事件列表判断是否结算。流局与结算分别记录。

#### 4.7.2 每项成立时机、公开范围与去重边界

**即时通知契约：**成功 reducer 返回后，服务端必须在本次权威推进中尽快生成成立事件，先于
该次 `settle()` 生成的计分事件，不等待后续响应、下一次操作或本手结束。成立事件记录规则事实，
`score-changed` 记录已经入账的分差；只在 `settle()` 中生成的计分事件不得成为即时通知的唯一来源。
两者仍随同一 room/match/回执事务提交，提交成功前不得对外发布。禁止为了先发通知而提前结算、
拆分事务、改变计分顺序或调整南京麻将规则。

当前真实顺序为 `applyAction → actionEvents → resultEvents → settle`；`startHand` 同样显式
调用 `applyAction(START_GAME)` 后生成动作/结果事件并立即 `settle`。`settle` 内先调用
`settlePendingScoringEvents`，再从旧 match 的 pending 生成 ScoreLine，最后生成 `score-changed`。
所以前三项的公开计分事件**晚于规则判定和成功 reducer 返回，但仍在同一次同步调用中**，不存在
源码证明的“等到手末才入账”。这段同步间隔不能作为已满足成立事件职责的依据。

自动推进可能在一次命令内合并多个转移，须保留每条已提交事件及顺序，不能只看最终快照现象。

- **花杠**：只消费实际创建且随成功转移提交的 `flower-kong-created` 所映射的公开成立事件。
  初始发牌/补花经 `startHand`，普通摸牌及杠尾补经 `apply`，均在 `settle` 前形成。同玩家同组合本手
  仅一次；运行期比较已有花组与新增花组，末张花抑制的新组合不能通知成功。连续补花形成不同组合
  是不同事件，不能按“本手已通知过花杠”全部压掉。开手历史不能从公开花牌重新拼出花杠。
- **四风归齐**：同一玩家连续多个出牌回合均为风牌且集齐四种，在补齐缺少风种的那次合法弃牌
  原子转移中成立；允许重复风和任意顺序，非风清零，成立后新序列可再次成立。`apply` 先记弃牌，
  先形成成立事件，`settle` 再记录该项分数，发生于后续响应裁决之前；不得等待本手结束再通知，也不将他人响应结果
  当作成立前提。不存在“看到四张风牌就由前端判定”的路径。
- **跟打一圈**：正常座次的第三名跟牌者合法打出相同牌面时成立，公开成立事件在该次弃牌的
  `settle` 之前生成，不能把调用 settle 当作规则成立时机。
  候选未完成、错牌、改变座次不能发成功；碰/明杠未改变预期座次可保留候选，暗杠/补杠不应被前端
  自行视为中断。末张普通牌弃出仍可能先成立，再于后续全过后流局。每次完成候选清空，下一轮另计。
- **锁两嘴**：仅当前规则版本、动作确实成功且受益者从非该关系状态进入“tracking 两嘴且有锁定
  责任人”的转移生成。正式碰、直接明杠的最终响应裁决及成功暗杠可能触发；收集意图、候选动作、
  被胡截断的碰杠、失败/尾补耗尽未推进嘴数均不得生成。两次纯暗杠的 null 责任人不构成锁定双方。
- **锁三嘴**：仅首次进入带有效 payer 的 active 时生成，不能只检测 after.active 每次都发。
  同一关系从两嘴到三嘴分配新的 ID；统一文案“B 已锁定 A 三嘴”已表达新等级，无需再存 previousLevel。
  两次无责任人暗杠后首次外部嘴可直接成为三嘴，只发三嘴，不补造两嘴。补杠、花杠不增加嘴数；
  active 的普通摸牌、弃牌、过轮、放弃特殊胡不产生新事件。不同来源使 tracking 永久 invalid 时
  不发两嘴/三嘴成功；过去两嘴通知是已发生历史，不宣称永久有效，不扩展为持续关系面板。

五类通知均向房间内四个玩家公开同一事件事实，不扩展为旁观者或房外广播。双方姓名只从
`RoomView.players[seat].name` 取值，始终附可区分座位，姓名缺失时使用座位称谓；不增加 session、
隐藏手牌、听牌集合、私有响应、内部 tracking 对象或 action token。显示锁定不表示已经收费、
触发三嘴包子或不过庄；不得改变规则第 20 章的胡牌、计分和责任关系。

最后 RoomView 而遗漏中间事件；产生的文字快照进入临时 FIFO 队列。事件 ID 去重，顺序水位只增不减，
不使用 revision、数组长度、文本、嘴数或 reason 去重；同等级新事实、两嘴→三嘴各按各自 ID 处理。
摸牌等被过滤事件也推进水位。只消费权威公开事件，不响应点击/ack 猜成功，不读取其他私有字段。

恢复与生命周期：首次载入和刷新不通知已有历史；disconnect 清空显示队列与消费基线，恢复后的
首份快照仅建立新基线，不弹离线积压；之后的新事件正常通知。流/轮询正常切换没有 disconnect
时保持消费基线，重复首帧不能重播。旧快照不降低水位；切换房间/room:left 清空房间消费状态，
新房间首份快照重新建立基线。同房间再来一将的 waiting 状态清空展示队列但保留递增编号水位。
正常跨手不清空尚未展示的事实，不因事件历史裁剪丢失已入队通知；不持久化客户端通知历史。

恢复专项揭示的边界：CloudSocket 在 connect 回调后同步 apply 恢复响应，但与断线前完全相同的
快照不会再次发 room:state。如果 App 只等下一次 room:state 建基线，会把真正的新事件误当历史。
最小处理留在 App：connect 回调排一个微任务；同步恢复回调若已到达则它正常建立基线，若没有
room:state 且旧 RoomView 仍在，则用已保留的权威 RoomView 建立基线（此时恢复内容相同）。
room:left/过期已清空视图时不回填。不得修改传输去重机制、推断新动作成功或重播历史；浏览器分别
覆盖“恢复内容相同后下一新事件”与“离线期间新增事件随恢复快照到达”两条路径。

展示：牌桌顶部独立的非覆盖式文字区域一次显示一条，普通开手/出牌/碰杠约 1.6 秒，胡/流局/
结算/特殊成立/锁定约 4.8 秒；同时到达的每条事实依次展示，不用最新一条覆盖队列。区域在缩放
牌桌外保持可读字号，牌桌剩余空间按现有 ResizeObserver 缩放，通知不挡牌面、合法操作或结算。
最终一将结束页面也继续展示待显示的终局通知；不改结算结构。姓名可换行，缺失身份安全降级。
使用 polite/atomic 的可访问文字提示，不自动夺焦点，无动画。

第 05 步 turn-banner/action-hint 及连接、暂停和错误提示保持原职责与优先级。连接中断、暂停、

## 6. 统一验收标准

V1.1 完成时必须同时满足：

- 玩家能够明确知道当前轮到谁、等待什么，以及牌局是否暂停；
- 碰、杠、胡等关键操作有明确的文字反馈；
- 操作提交与操作成功不会混淆，超时也不会被误报为明确失败；
- 特殊响应、抢补杠胡、多家胡牌等情况下，反馈与最终规则结果一致；
- 最近牌桌记录能够在刷新和重连后恢复，并符合数量、顺序和房间生命周期约定；
- 结算摘要清楚，详细计分、承包和逐笔付款仍可查看；
- 音效可关闭，动画不会阻碍正常操作，并尊重减少动态效果偏好；
- 不泄露任何玩家的隐藏信息；
- 不破坏已有规则测试、服务端测试、云端测试、类型检查、lint、格式检查、构建和四人联机流程。
