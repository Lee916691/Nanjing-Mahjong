# 新增双人模式：设计与开发计划

> 日期：2026-10-19
> 状态：00～04已完成；05自动化回归与文档同步完成，真人自然一将、实机及线上验收待完成。
> 运行规则：四人敞开头V1.0.11、双人敞开头V1.0.12。GitHub交付见实施记录，尚未部署。

## 1. 背景、目标与文档职责

现有好友房要求四人齐备，两名好友无法直接开局。本次新增独立双人模式，沿用现有144张
南京敞开头基础规则、权威服务端和好友房流程；创建房间时选择双人或四人，原四人体验不变。

文档职责如下，避免产生两套裁判依据：

- [规则规范第29章](nanjing-mahjong-rules.md)：唯一双人规则来源，
  包括金额、胡牌资格、自摸软花、包子、有效庄次和全部边界。
- 本文：产品流程、技术设计、接口与存档契约、实施顺序、验收及实际完成状态。
- [产品需求](product-requirements.md)、[架构](architecture.md)：通过增量章节接入本设计，保留原四人基线。
- [实施状态](implementation-status.md)：记录实际已执行项目，不把设计、历史回归或计划当作新功能通过。

如实现发现规则遗漏，先记入[待确认问题](open-questions.md)，停止相关实现并向用户报告；
若技术设计不适用，先更新本文再修改测试及代码，不改变规则使测试通过。

## 2. 已确认范围与不变要求

| 维度           | 双人目标                                                            |
| -------------- | ------------------------------------------------------------------- |
| 人数与牌库     | 两名真实玩家、完整144张，无AI或虚拟座位                             |
| 计分           | 456花二、比下胡；胡牌及包子一份，抢补杠无×3                         |
| 新软花         | 真实自摸及按自摸结算的包子加2，仅双人、一次，具体排除见规则第29.4节 |
| 三嘴与其他包子 | 保留原机制、资格、优先级、特殊胡及不过庄；仅按已确认差异计分        |
| 实时分         | 以规则第29.5节实际金额为准；双人暗杠实际20                          |
| 停用规则       | 跟打一圈、四风归齐不生成事件、付款或续庄事实                        |
| 一将           | 8个有效庄次、四圈；末庄特殊续庄移到第8庄                            |
| 房间节奏       | 两人在线准备后开始；任一离线暂停；45秒结算或两人确认后提前继续      |

不改变四人规则与存档语义、牌面美术、服务端权威、私有视图、匿名Cookie身份、命令幂等、
断线接管、房间有效期和既有提前结束权限。原四人基线中的所有规则测试仍须通过。

不在本次范围：三人模式、删减牌库、AI补位、自动托管、匹配/排位、账号、观战、回放、
新音效素材、可任意组合的规则编辑器、跨设备找回身份、存储架构更换及线上部署。
新建房间后模式固定；再来一将也不换模式。需要不同模式时新建房间。

## 3. 产品流程与界面约定

1. 创建页提供“四人敞开头”和“双人敞开头”，默认四人，选择后再创建。
2. 房间卡片与候场显示权威模式、容量和一将有效庄次数；加入页说明模式由房间决定，成功
   入座后展示服务端确认的信息，不为入座前预览新增公开接口。邀请链接仍只定位房间，
   不能靠URL参数改变已存在房间模式。
3. 双人候场只显示两个真实席位；满两人拒绝第三人。两人在线且准备后由房主开始。
4. 牌桌自己在下方、唯一对手在上方；四人继续现有四向布局。双人不显示两个虚假空座。
   玩家称呼优先使用“你”、姓名及“对手”；逻辑索引与桌面方向分离，不增加座风计分。
5. 中央局况显示当前有效庄次/8、圈次、手数、庄家、行动位和余牌。第8庄显示末庄状态；
   不能继续显示“第16庄”或把实际手数当作有效庄次。
6. 手牌、牌河、副露、花牌、架牌、暗杠外背内明、选牌确认、全屏和无障碍功能沿用。
   副露来源牌应按对手方向展示，不能沿用四人`%4`计算导致来牌方向错误。
7. 即时通知、最近历史、音效及轻量动画复用现有公开事件。双人不出现已停用规则的通知。
8. 单手摘要展示双方分差与累计分；详情显示最终一条胡牌付款及各项真实实时付款。
   自摸加花单列“自摸加花2”，花分为翻倍前4、最终增加8；抢补杠不显示×3。
   三嘴/包子仍说明强制牌型与责任，不再显示“三份”或“三家付款”。
9. 结算确认进度按0/2、1/2、2/2显示；双方确认或45个有效秒到期仅推进一次；暂停冻结。
   最终一将完成后只显示最终结果与既有管理操作，不能再次确认开启第9个有效庄次。
10. 再来一将清空准备、分数、结算确认、当将事件及临时反馈，保留房间模式和合法座位。
    房间事件编号继续沿用现有不复用约定；暂离、重连、提前结束和失效仍走原流程。

人工布局至少检查1366×768桌面及390×844窄屏，覆盖长姓名、大量弃牌/花牌/副露、历史和
结算同时展开、负分和并列排名；两方均须可操作并看清中央局况，不以隐藏历史数据解决拥挤。

实现中视觉复核：四人桌的整体缩放在390像素宽的双人页面仍导致手牌/文字过小。双人窄屏
改为不缩放的纵向两席排布，房间栏允许换行，自己的手牌以至少36像素宽横向滚动，公开牌河
保持独立滚动；页面允许纵向滚动到操作区。此调整仅限双人窄屏，桌面和四人继续原缩放布局。

## 5. 技术设计与数据流

### 5.1 模式标识与单一来源

沿用已有RuleSet注册边界，只新增一个双人标识，不再引入平行的`mode`、`isDuo`等可互相矛盾字段：

| `ruleSetId`        | 名称       | 玩家数 | 总有效庄次 |
| ------------------ | ---------- | -----: | ---------: |
| `nanjing-open`     | 四人敞开头 |      4 |         16 |
| `nanjing-open-duo` | 双人敞开头 |      2 |          8 |

- 原默认ID保持`nanjing-open`。RuleSet增加只读人数元数据，人数与现有总有效庄次数共同由注册项定义。
- `SavedRoom.ruleSetId`是房间级权威模式；创建后不可由加入、动作、重新开将等命令更换。
  `MatchState.ruleSetId`和`GameState.ruleSetId`沿用现有字段，必须与房间一致。
- 成员、玩家、比分、声明/三嘴等按所选人数创建。双人长度为2，四人为4；不靠在线人数、
  当前成员数、客户端参数或空座情况推断玩法。所有玩家索引均须小于本模式人数。
- 保留已有`totalEffectiveDealerTurns`，校验其与所选注册项一致，不接受客户端任意设置。
- 结构校验、花牌处理和南京基础牌型尽量复用现有函数；不复制整套引擎，也不引入插件框架、
  动态规则DSL或仅为两个固定模式建立复杂配置层。

### 5.2 创建命令和公开视图契约

下列契约已写入共享类型及运行时实现；旧格式的可选字段仅用于读取兼容：

| 对象                         | 字段与约束                                                                                               |
| ---------------------------- | -------------------------------------------------------------------------------------------------------- |
| `room:create`的`RoomCommand` | 新增可选`ruleSetId`，只接受上表两个ID；缺省仍创建四人，显式`null`、未知值和错误类型均拒绝                |
| 其他命令                     | 不允许携带模式变更字段；加入只定位房间，准备/动作/再来一将等不能修改规则集                               |
| `RoomView`                   | 新增必需`ruleSetId`与`totalEffectiveDealerTurns`；既有`players`、`effectiveTurn`、`dealer`等按本模式返回 |
| `SavedRoom`                  | 新格式中必需`ruleSetId`；成员长度、规则版本、Match/Hand模式和人数必须一致                                |
| 软花内部来源                 | `SoftFlowerKind`增加`self-draw`，合法计次固定为2；作为软花项保存，不加入`HuPattern`                      |

共享契约使用相同字面量，不为复用这两个标识新增包或让规则引擎依赖UI/网络类型。
创建请求仍携带`commandId`；模式加入现有命令载荷和指纹，同一ID重试不重复建房，换模式的
不同载荷不能复用旧ID。保留旧指纹算法和已存回执，不为了默认值规范化重写旧回执。
原Node路径的新回执在既有JSON body内保存`ack`与`fingerprint`，不增加数据库列；读取兼容
旧的纯ack记录，只有新记录可验证载荷冲突，旧记录保持原样重放，不伪造历史指纹。

`RoomView`是逐玩家安全视图；新增公开元数据不能把原私有手牌、听牌集合、响应队列或令牌
变成共享数据。客户端根据元数据展示模式，所有合法操作仍仅来自服务端签发的choices/token。
前后端需一起交付；新客户端遇到未知模式、人数或进度不一致时停止提交并提示刷新/错误，
不能降级猜测成四人。缺省创建兼容不代表旧构建已经支持双人布局。

### 5.3 权威计分顺序与一次加花

```text
玩家提交服务端动作token
→ 服务端验证身份、房间、epoch和合法意图
→ game-core按真实来源验证结构/资格与原有特殊胡条件
→ 确定最高优先级包子、最终强制牌型及是否按自摸结算
→ 双人非天胡且符合规则第29.4节时，在最终evaluation中确保恰有一项self-draw/count=2
→ RuleSet生成最终金额及一条胡牌付款快照
→ 校验结果/evaluation/付款/事实一致，原子保存并执行快照
→ Match按结果和合法事实决定过庄，服务端生成公开事件与计分说明
→ 客户端展示权威安全视图
```

现有代码有普通胡、三嘴特殊胡、自然胡转包子、第四副露强制包子等不同入口，不能只在普通
自摸入口加2。按现有边界提取最小共用计算，或让各入口调用同一归一化步骤；无论具体实现，
必须先确定最终包子资格再生成付款，不能先按普通点炮付完后补发8分。

- availability/地胡听牌判定与实际结算使用相同合法资格；计分加花不得创造新听口。
- 同一次真实自摸先得到本项、后升级包子时，保持一项count=2；不能变为count=4。
- 点炮转包子需要补入该软花，并同步最终HandResult、计分事件及说明；普通点炮、抢补杠、
  天胡、流局和四人evaluation不能混入此项。
- 双人自然胡转包子后，`WinHandWinner`保存可选`packageKind`（three-mouth/three-pure/global）
  与事件一致，作为真实弃牌来源下“按自摸结算”的权威摘要，供结果/恢复校验使用；不能仅凭
  软花本身或全球牌型猜测已发生包子。旧四人结果仍允许缺省，历史不补造此字段。
- 原真实`HuSource`、winning tile、触发者和花开/杠开provenance保留；不能伪造摸牌来源
  来获得这项加分。现有三嘴`settlementMode`和包子事实可用于计分判断。
- `score-explanation.ts`从同一最终evaluation及付款快照解释“自摸加花2”，不再硬编码所有
  抢补杠×3或所有暗杠基础5。若实现需要额外模式上下文，应为最小权威参数，不能从总金额猜模式。
- 一次胡牌一条付款；真实实时杠分另行保存。三嘴与三清同触发时按原优先级决定该次杠是否
  成立，不能将低优先级规则的临时计分泄漏到最终事件。
- 通用settlement继续校验和执行最终快照，不重算南京规则；对付款拓扑的验证须结合模式，
  不能简单把原四人“三条”条件放宽为任意数量。

### 5.4 一将推进与停用规则

总有效庄次数取RuleSet；圈次由两人每圈两个有效庄次计算，实际手数单独保留。
正常轮转只访问实际玩家；准备下一手也按同一模式重新创建玩家、比分引用和局内状态。

- 第8庄为双人末庄；沿用原completion与事实校验边界，仅按规则第29.7节选择续庄条件。
- 自摸加花属于`softFlowerItems`，不新增`HuPattern`、大牌标记或续庄计数，避免普通自摸
  因多一个“牌型”而被误判为大牌。原有自摸计数仍可记录，不能恢复已删除的独立续庄条件。
- 双人停用规则在权威发生点不产生成立/计分事件或非零事实；不能只隐藏UI消息而继续扣款。
  共享事件类型保留四人支持；不删全局四风归齐/跟打一圈类型或破坏旧事件解析。
- 若复用既有事实结构，双人两项停用计数保持0；恢复时发现非零视为损坏，不静默应用。
- 局结束、下一手、再来一将按现有生命周期清理三嘴、承包、架牌、地胡、过手、响应与确认，
  重复完成或过期token不能导致重复计分、多开一手或越过第8庄结束条件。

## 6. 存档、传输与错误处理

### 6.1 格式与规则版本

采用现有房间JSON持久化，默认不新增D1表或迁移。为使旧程序拒绝新语义而非误按四人读取，
共享`SavedRoom.format`设计升级为2；新增房间及兼容旧房间的下一次正常原子保存使用格式2。
`CloudRoom.cloudFormat`继续为1，因D1封装方式不变；不能用cloudFormat掩盖共享格式不兼容。

| 存档情况                                                | 后续读取行为                                                      |
| ------------------------------------------------------- | ----------------------------------------------------------------- |
| 旧`format: 1`，无`ruleSetId`，原合法四人规则版本        | 仅按四人恢复；内存补默认ID，保留原四人兼容；下一次正常保存写格式2 |
| 新`format: 2`、`nanjing-open`                           | 四人成员和Match/Hand必须一致；新四人规则标记仍为V1.0.11           |
| 新`format: 2`、`nanjing-open-duo`                       | 必须两人成员、双人Match/Hand、8庄、双人规则标记V1.0.12            |
| 新格式缺模式、旧格式含双人、新格式模式与规则/人数不一致 | 拒绝，不回退四人、不修剪或补造玩家                                |
| 未知格式、未知模式、非法索引或损坏结果/事件/付款        | 拒绝并返回既有兼容/操作错误，不部分写回                           |

四人旧V1.0.8整将的三嘴兼容、V1.0.9/V1.0.10读取升级至现有V1.0.11的行为保持。
不能给旧历史增加自摸软花、合并原三份付款或重算累计分；旧档已有四人16庄不缩成8庄。
原事件schema版本1/2、事件计数器和裁剪兼容保留；解析后的座位须再按房间模式校验。

原Node SQLite全库metadata带规则版本，现已为混合房间改为可识别新容器的
`2:room-modes`标记，接受既有合法旧metadata，并在正常提交事务中升级；具体房间规则由
房间自身决定，不用一个全库规则号把四人房间改为双人。旧二进制应明确拒绝新容器；回滚须
使用发布前的原版本备份，不能承诺旧程序可直接读取新档。本次不执行生产数据库操作或部署。

### 6.2 原子性与全部入口

- Node `Store.rooms()`和Cloud `poll()`、`context()`、`room()`统一走相同的模式恢复与校验，
  不能只在首次connect校验，而在轮询、已建立NDJSON流或动作加载时遗漏。
- 沿用D1版本比较、失败重试、命令回执和Node事务；只有保存成功后发布新视图。
- 同命令重试不重复创建模式、加花、付款或事件；并发满座/准备/结算确认只提交一次有效结果。
- 非法模式为`BAD_REQUEST`，第三人入座为`ROOM_FULL`，人数/准备不足为`NOT_READY`；
  沿用`FORBIDDEN`、`PAUSED`、`STALE_ACTION`等错误，不暴露服务端私有状态。
- 存档损坏、编号耗尽、付款拓扑或evaluation不一致时，拒绝整个相关动作及写入，不丢弃
  部分记录后继续游戏，不把未知模式当默认值，不向客户端泄露原始存档、密钥或会话。
- 模式/人数/规则版本不兼容统一返回`ROOM_MODE_ARCHIVE_INCOMPATIBLE`（HTTP 503或已开流的
  error帧并结束）；保留原事件存档错误码及文案，避免把模式损坏误报为事件历史损坏。
- 邀请链接、匿名身份、接管、租约、30分钟失效、NDJSON重连/轮询回退与revision去旧保护不变。
